# 自动记账效率基准（2026-11-19）

复现命令（在仓库根目录）：

```bat
gradlew.bat :app:testDebugUnitTest --tests "*AutoBookkeepingBenchmarkTest*" --tests "*AutoBookkeepingDbBenchmarkTest*"
```

两份测试都跑真实业务代码：`NotificationRouter`（设置读取 → 来源闸门 → 解析）、
`CandidateProcessor`（去重查询 → 组装 → 写库）。差别只在仓库实现：

- `AutoBookkeepingBenchmarkTest` 用内存仓库，测解析与去重的纯 CPU 成本，2 万条取分布；
- `AutoBookkeepingDbBenchmarkTest` 用内存版 Room（底层是真 SQLite），测「通知 → 真正落库」的端到端延迟。

限制：这是 JVM 上的数值，不含系统唤醒通知监听进程的时间；
真机冷启一次监听回调大约再多几十毫秒，但一天几十上百条通知的增量成本可以忽略。

## 语料

30 条真实格式通知：微信支付 9 条（其中 3 条营销/冲突文案必须挡掉）、支付宝 11 条
（含账单、优惠券、余额宝收益）、银行 8 条（工行、招行）、聊天里的金额 3 条（必须不记）。
命中率只统计 20 条常规样本；9 条对抗样本单独统计误报；余额宝收益属于已知未覆盖。

## 结论

1. **速度不是瓶颈**：解析 28 µs、含去重 35 µs、含 SQLite 落库 1.5 ms/条。
   一天 200 条通知的 CPU 总成本约 7 ms，落库约 0.3 s，可以忽略不计。
2. **瓶颈是「待核对」比例**：20 条常规样本里只有 3 条（15%）能直接入账，
   因为微信/支付宝通知普遍不带商户名，`CandidateProcessor` 一律降级为待确认。
   想提高自动入账率，应该做商户规则学习（`MerchantRuleEntity` 已有），让「瑞幸咖啡」
   这类历史商户下次直接归到「餐饮」，而不是继续放宽解析器的置信度。
3. **去重有效**：同一条通知重复投递不会重复记账；超过 2 分钟窗口再投递会重新入库，
   这是刻意的（避免把真实的两笔同额支付误判为重复）。
4. **未覆盖**：余额宝收益这类「小额理财入账」目前识别不到，如果需要可以单独加一条规则。
