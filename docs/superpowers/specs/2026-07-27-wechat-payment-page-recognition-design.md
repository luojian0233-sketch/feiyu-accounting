# 微信支付页面识别设计

日期：2026-07-27
状态：已获用户口头确认，待书面审阅

## 背景

PKG110（Android 16 / API 36）真机验收发现：微信支付通知的真实格式为标题“微信支付”、正文“已支付¥金额”。现有解析器只识别“支付成功”“付款成功”“扣款成功”，因此没有生成交易。

通知可以可靠提供支出方向和金额，但不含商户、支付方式或消费分类。微信内部“微信支付”页面会显示商户、金额、支付方式和时间，但普通通知读取服务受 Android 应用沙箱限制，不能直接读取另一个应用的内部页面。

用户当前以自用和效率优先，接受主动开启无障碍服务，并在支付后点击微信支付通知打开微信页面。后期发布时需重新评估 Google Play 的无障碍 API 申报、显著告知和同意要求。

## 目标

1. 精确识别真实微信通知“微信支付 / 已支付¥金额”，立即生成一笔支出待确认记录。
2. 用户打开微信支付页面后，自动提取商户、金额、支付方式和可见时间。
3. 将页面结果唯一匹配到最近的微信待确认记录，自动补全商户并应用分类规则。
4. 对“中国电信”“中国移动”“中国联通”等明确商户自动归类为“通讯”。
5. 未知商户让用户选择一次分类并保存商户规则，以后自动归类。
6. 不保存微信页面原文或截图，不上传识别数据，不控制微信界面。

## 非目标

- 不自动点击、滑动、付款、退款或打开微信内部页面。
- 不绕过微信或 Android 的权限、安全和隐私控制。
- 不读取微信聊天、联系人、余额、订单号或与记账无关的页面。
- 不依据缺少商户信息的通知猜测餐饮、购物等消费分类。
- 本次不实现支付宝页面识别；支付宝继续使用现有通知链路。

## 方案选择

采用“精确通知解析 + 限定微信的无障碍页面识别 + 本地 OCR 回退”的混合方案。

未采用仅新增通用关键词的方案，因为微信聊天正文也可能出现“已支付”，会提高误记风险。未采用纯截图分享方案，因为用户当前优先效率。未采用自动操控微信方案，因为它超出记账所需范围并增加安全风险。

## 架构

### 1. 精确通知解析

`WechatParser` 增加微信官方模板分支，必须同时满足：

- 来源包名精确等于 `com.tencent.mm`；
- 用户已开启“微信支付通知”来源；
- 标题去除首尾空白后精确等于“微信支付”；
- 正文去除首尾空白后符合“已支付 + 唯一人民币金额”；
- 正文不含多个人民币金额、促销语、转账或方向冲突信号。

匹配后生成：

- 方向：支出；
- 事件类型：支付；
- 商户：空；
- 低置信度；
- 分类：“待确认”；
- `pendingConfirmation = true`。

该记录在页面补全前不计入统计。现有去重键继续阻止同一通知重复入账。

### 2. 无障碍服务

新增专用于微信页面识别的 `AccessibilityService`：

- 只订阅 `com.tencent.mm`；
- 只接收窗口状态变化和窗口内容变化事件；
- 声明读取窗口内容和截图能力；
- 不声明手势操作能力；
- 不调用点击、滑动、返回、全局操作或输入 API；
- 必须由用户在系统设置中主动开启，也可以随时关闭。

设置页新增独立的功能说明、当前状态和系统无障碍设置入口。通知读取权限与无障碍权限互不替代、分别显示。

### 3. 页面识别

页面处理分两级：

1. 优先遍历无障碍节点树，读取可见文字与边界。
2. 节点信息不完整且设备为 Android 11（API 30）或更高时，调用无障碍截图 API，并使用随 APK 打包的中文 OCR 模型在本机识别。

只有同时出现页面签名“微信支付”和支付卡片结构（商户、人民币金额、“账单详情”或“使用…支付”）时才继续。OCR 结果保留行和边界，用于区分页面中多张支付卡片；默认只处理最上方、最新的可见支付卡片。

位图和完整 OCR 文本仅存在于内存，处理结束立即释放。日志、数据库、备份和诊断信息不得包含截图或页面原文。

API 26–29 设备若节点树信息不足，不进行自动截图，记录脱敏失败原因并保持待确认；可在后续版本提供用户主动分享截图的回退入口。当前主验收设备 API 36 支持完整流程。

### 4. 待确认记录匹配

页面识别结果只匹配满足以下条件的交易：

- 来源为微信通知；
- `pendingConfirmation = true`；
- 方向为支出；
- 金额完全相同；
- 通知时间与页面识别时间相差不超过 15 分钟。

匹配候选为零时不创建第二笔交易。候选多于一笔时不自动修改，向用户显示候选选择，防止同金额连续支付被错配。只有唯一候选才允许自动补全。

### 5. 商户分类与规则学习

复用现有 `merchant_rules` 表，不新增数据库表：

- 商户名称先做去空白、统一全半角和大小写等规范化；
- 内置高确定性关键词：“中国电信”“中国移动”“中国联通”映射到“通讯”；
- 已存在的用户商户规则优先于内置规则；
- 命中规则时更新待确认交易的商户、分类和支付账户，并取消待确认；
- 未命中规则时仅补全商户和支付方式，继续待确认；
- 用户确认未知商户并选择分类时，保存精确商户规则，供以后复用。

如果目标分类已隐藏或不存在，不自动确认，保持待确认并让用户选择当前可用分类。

### 6. 支付方式

“使用零钱支付”等页面字段映射到账户名称。账户存在且可用时自动选择；账户不存在时不静默创建，先保留为交易备注中的结构化提示并让用户确认是否新增账户，避免账户列表被 OCR 误识别污染。

## 状态与用户体验

典型流程：

1. 微信发布“微信支付 / 已支付¥1.00”通知。
2. 自记账生成“¥1.00 支出 / 待确认”记录，并发送本地提醒。
3. 用户点击微信通知并打开微信支付页面。
4. 页面识别得到“中国电信 / ¥1.00 / 零钱”。
5. 系统唯一匹配待确认记录，并将“中国电信”归为“通讯”。
6. 记录变为已确认并进入日、周、月、年统计和饼图。

设置页应清楚显示：

- 通知读取权限状态；
- 微信来源状态；
- 微信页面识别状态；
- 最近一次脱敏诊断结果，例如“未发现待匹配记录”“同金额记录不唯一”“页面字段不完整”，不得显示原文。

## 错误处理

- 权限未开启或被撤销：停止页面读取，保留通知待确认记录，应用继续支持手动记账。
- 页面不是微信支付页：忽略，不产生诊断噪声。
- OCR 无结果或字段不完整：保持待确认，不猜测商户或分类。
- 多个金额、多个候选或方向冲突：保持待确认并要求人工选择。
- OCR 模型异常：记录脱敏错误类型，不保存图片或原文。
- 数据库更新失败：不改变原记录，显示可重试提示。
- 服务或进程重启：不得重新导入已经确认或已有去重键的通知记录。

## 隐私和安全边界

- 无障碍服务只配置微信包名，不扫描其他应用。
- 页面识别只在微信处于当前活动窗口时运行。
- 不申请 `INTERNET` 或广泛存储权限；OCR 使用随 APK 打包的中文模型。
- 不保存截图、完整页面文本、聊天内容、账号、余额或订单号。
- 仅持久化交易所需的金额、方向、商户、分类、时间、支付账户和脱敏去重信息。
- 启用无障碍服务前必须显示独立、明确的用途说明和用户主动同意。

## 测试设计

严格按测试驱动开发执行。

### JVM 单元测试

- “微信支付 / 已支付¥1.00”生成支出待确认候选。
- 错误标题、无货币标识、多个金额、促销语和方向冲突均拒绝。
- 现有微信、支付宝和银行解析测试不回归。
- 无障碍节点文本可提取商户、金额、支付方式和卡片顺序。
- OCR 结构结果与节点结果归一为同一页面模型。
- 金额相同且 15 分钟内的唯一待确认记录可匹配。
- 零候选或多候选不自动更新。
- 电信运营商映射到“通讯”。
- 用户商户规则优先于内置规则。
- 隐藏或不存在的分类不自动确认。
- 未知商户补全商户但保持待确认。
- 完成确认时保存商户规则。

### Android 仪器测试

- 设置页显示无障碍权限说明和状态。
- 权限开启、撤销及进程恢复不会崩溃。
- 模拟微信页面节点事件只处理 `com.tencent.mm`。
- API 30+ OCR 回退不写入截图文件。
- 页面识别成功后 UI、统计和饼图只增加一笔交易。

### 真机验收

在 PKG110（Android 16 / API 36）上：

1. 覆盖安装保留现有账本。
2. 开启通知读取、微信来源和微信页面识别。
3. 产生一笔小额微信支付。
4. 确认通知先生成待确认记录。
5. 点击微信通知打开支付页面。
6. 确认商户、金额、支付方式和分类正确补全。
7. 确认只生成一笔交易，统计和饼图金额正确。
8. 重复打开同一页面，确认不会重复入账。
9. 连续两笔同金额支付时，确认不会错配。
