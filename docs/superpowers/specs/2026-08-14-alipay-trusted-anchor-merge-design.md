# 支付宝可信锚点混合识别设计

## 背景与根因证据

PKG110（Android 16 / API 36）上的既有支付宝账单详情页运行在 `com.eg.android.AlipayGphone/com.alipay.mobile.nebulax.xriver.activity.XRiverActivity`。应用总开关、支付宝来源和无障碍服务均已确认开启。

脱敏真机探针得到两个确定结果：无障碍截图返回 `CAPTURE_SUCCESS`；同一帧进入现有 `ScreenshotRecognitionController` 后返回 `REJECTED_NOT_PAYMENT_PAGE`。交易总数保持 2，证明失败发生在 OCR 快照进入 `AlipayPageParser` 的阶段，未进入协调器或持久化。

同页无障碍树包含精确的支付宝账单详情签名，但金额等关键字段不可访问；截图 OCR 可补充视觉字段，却可能丢失或合并页面标题，导致现有解析器没有语义锚点可建立账单分组。

## 目标

在不放宽全局支付宝页面签名、不信任无障碍树中的金额或方向、也不增加原始数据持久化的前提下，允许已被无障碍树精确证明为支付宝账单详情页的 OCR 结果复用可信语义锚点。

## 非目标

- 不允许普通支付宝页面、未知包名或第三方页面借助宽松文字包含规则触发记账。
- 不修改微信空 WebView 的现有处理路径。
- 不从无障碍树复制金额、方向、商户、账户或时间。
- 不新增网络、存储、悬浮窗或手势权限，不保存截图、OCR 原文或页面原文。
- 不改变 `AlipayPageParser` 的金额、方向冲突、几何归属或时间规则。

## 设计

### 可信锚点选择

新增一个纯函数，从原始 `PageSnapshot` 中筛选精确文本等于以下任一值的元素：

- `支付宝`
- `账单详情`
- `账单明细`

筛选前只允许包名精确等于 `com.eg.android.AlipayGphone`。比较使用 `trim()` 后的完整相等，不使用 `contains`、正则近似或 OCR 纠错。

### 混合快照

截图 OCR 完成后，控制器按以下规则构造待解析快照：

1. 微信、未知包名或原始快照没有可信支付宝锚点：直接使用现有 OCR 元素，不混合。
2. 支付宝且原始快照至少有一个可信锚点：把可信锚点与 OCR 元素合并。
3. 使用 `trim()` 后文字和完整 `TextBounds` 作为去重键；若 OCR 已包含相同锚点及相同坐标，只保留一个。
4. `observedAt` 和包名继续取原始快照；所有非锚点业务字段只能来自 OCR 元素。

合并后的快照仍交给现有 `AlipayPageParser`，因此候选生成、置信度、摘要、协调器去重和待确认逻辑均保持原样。

### 失败与所有权

- 截图包名与原始包名不一致时继续拒绝并回收位图。
- 截图、OCR、设置读取和取消语义保持现状；取消必须继续向上传播。
- 混合后仍被解析器拒绝时不得调用协调器或写入数据库。
- 捕获位图仍由现有 `try/finally` 恰好回收一次。

## 测试设计

严格执行 RED→GREEN：

1. 真实失败形态：原始支付宝快照只有精确 `账单详情`，OCR 只有 `¥1.00` 等视觉字段、没有任何详情或事件锚点；旧代码应零处理，修复后应只处理一笔支付宝支出。
2. 原始快照没有精确可信签名时，即使 OCR 有金额也不得补锚点或调用协调器。
3. 原始无障碍金额、方向、商户、账户和时间不得进入混合 OCR 快照。
4. OCR 已含相同签名与坐标时必须去重，避免重复语义锚点改变分组。
5. 微信空 WebView、支付宝完整页、截图包名不匹配、OCR 异常、取消和位图回收的现有回归测试继续通过。
6. 运行相关 accessibility/capture/recognition 单测、fresh 全量 JVM、Lint、AndroidTest 编译和 Debug APK 构建。

## 真机验收

1. 用 `adb install -r` 覆盖安装并确认现有交易、设置和授权保留。
2. 打开同一笔已有支付宝支付详情，不产生新付款。
3. 预期只新增一笔金额和方向正确的支付宝待确认记录；确认后只计入一次。
4. 重新打开同一详情并停留超过去重窗口，交易总数不得再次增加。
5. 全程不运行 connected 测试、不卸载、不清除应用数据；所有直接 ADB 命令使用 10 秒超时。
